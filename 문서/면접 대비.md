# 면접 대비

> 채용 면접관(CEO) 관점에서 이 프로젝트에 대해 물어볼 수 있는 기술 질문과 답변

---

## Q. 왜 게임 엔진(Unity/Unreal) 대신 웹 기반으로 만들었나요?

**A.** 이 프로젝트의 목적은 "현실 공간 + 3D 모델 합성"이라는 단일 목적에 집중하는 것입니다. 게임 엔진은 범용 도구라 기능이 과하고 진입장벽이 높습니다. 웹 브라우저만으로 설치 없이 즉시 사용 가능하게 만들어 타겟 사용자(VTuber, 크리에이터)의 접근성을 높였습니다.

## Q. 파이프라인 아키텍처를 왜 이렇게 설계했나요?

**A.** 3DGS 분야는 새 모델이 빠르게 나옵니다. End-to-End 모델, 동적 물체 제거 전처리, 학습 기반 초기화 등 단계 수와 순서가 모델마다 다릅니다. 고정 파이프라인으로는 매번 구조를 뜯어야 하므로, Stage + Recipe 구조를 채택했습니다. Stage 하나 추가 + Recipe yaml 작성만으로 새 모델에 대응 가능하고, Orchestrator와 기존 Stage는 수정하지 않습니다. 이 패턴은 PyTorch Lightning, Nerfstudio, FastGS(CVPR 2026) 등 최신 프레임워크들이 동일하게 사용하고 있습니다.

## Q. 왜 최신 3DGS 모델 대신 원본 3DGS부터 시작했나요?

**A.** 베이스를 이해해야 확장 시 올바른 판단이 가능합니다. 원본 3DGS로 파이프라인을 완성한 뒤, 다른 모델(Mip-Splatting 등)로 교체하여 결과를 비교하면 "어떤 모델이 어떤 상황에서 더 나은지" 근거 기반으로 판단할 수 있습니다. 또한 Recipe만 바꿔서 모델을 교체했다는 것 자체가 아키텍처 설계력의 증명이 됩니다.

## Q. COLMAP을 왜 직접 구현하지 않았나요?

**A.** COLMAP은 SfM(Structure from Motion)을 수행하는 오픈소스로, SIFT 특징점 검출, 번들 조정, 삼각측량 등 컴퓨터 비전 분야에서 수십 년간 연구된 결과물입니다. 이걸 직접 구현하면 그게 COLMAP을 만드는 프로젝트가 됩니다. 이 프로젝트의 목적은 파이프라인을 설계하고 운영하는 것이지 SfM을 연구하는 것이 아닙니다. 또한 COLMAP을 대체하는 학습 기반 모델(DUSt3R 등)이 이미 나오고 있어, Stage 교체로 대응하는 것이 합리적입니다.

## Q. 새로운 3DGS 모델이 나오면 어떻게 대응하시겠어요?

**A.** Stage + Recipe 구조 덕분에, 새 모델이 나오면 해당 역할 폴더에 Stage 파일 하나를 추가하고 Registry에 등록한 뒤 Recipe yaml을 작성하면 됩니다. Orchestrator나 기존 Stage를 수정할 필요가 없습니다. 실제 프로덕션 환경(Polycam, 평행공간 등)에서도 오픈소스 기반으로 시작해서 자사 도메인에 맞게 최적화하는 방식을 사용합니다.

## Q. Windows에서 PyTorch 환경 설정 시 어떤 문제가 있었고 어떻게 해결했나요?

**A.** conda로 PyTorch를 설치하면 MKL의 libiomp5md.dll과 PyTorch의 libomp.dll이 충돌하여 DLL 로딩 에러가 발생합니다. conda는 Python 환경 관리에만 사용하고, PyTorch는 pip + --index-url로 CUDA 11.8 전용 빌드를 설치하여 충돌을 원천 차단했습니다.

## Q. Stage + Recipe 구조에서 Strategy Pattern을 어떻게 적용했나요?

**A.** `BaseStage` 추상 클래스가 `run(config, context)` 인터페이스를 정의하고, 각 Stage(Colmap, Dust3r, GaussianSplatting 등)가 이를 구현합니다. Orchestrator는 구체 클래스를 모르고도 동일한 인터페이스로 호출할 수 있어, recipes.yaml에서 Stage 이름만 바꾸면 알고리즘이 교체됩니다. 엄밀히 말해 정통 GoF Strategy 패턴은 런타임 중 교체를 가정하지만, 우리는 실행 시점(launch-time)에 yaml로 결정한다는 점이 차이입니다. 이는 Plugin / Configuration-driven Pipeline 패턴에 가깝고, 최신 ML 프레임워크들이 동일한 방식을 사용합니다.

## Q. config와 context는 어떻게 다른가요?

**A.** config는 yaml에서 로드한 **고정 설정값**(경로, 학습 파라미터 등)으로 실행 중 변하지 않습니다. context는 **Stage 간 결과 전달용 딕셔너리**로, 빈 상태로 시작해 각 Stage가 자신의 결과물(프레임 경로, 포인트 클라우드 경로 등)을 누적해 넣습니다. Stage들이 서로를 직접 호출하지 않고 context라는 공통 컨테이너로만 통신하기 때문에, Stage 간 결합도가 낮아집니다.

## Q. Recipe yaml을 파일별로 분리하지 않고 하나로 합친 이유는?

**A.** Recipe별 파일 분리는 새 조합이 늘어날 때마다 파일이 늘어나는 단점이 있습니다. 하나의 `recipes.yaml`에 여러 recipe를 키로 묶어두면, 새 조합 추가 시 yaml에 블록만 추가하면 되고 모든 조합을 한 곳에서 비교할 수 있습니다. `--recipe colmap_3dgs` 같은 인자로 키만 선택하면 됩니다.

## Q. Registry를 자동 스캔(importlib) 방식으로 만들지 않은 이유는?

**A.** 자동 스캔은 Stage가 수십 개일 때 가치 있는 추상화입니다. Phase 1의 Stage가 4개인 상황에서는 단순 딕셔너리가 더 명확하고 디버깅하기 쉽습니다. "어떤 이름이 어떤 클래스로 연결되는지" 한 파일만 보면 즉시 파악 가능합니다. Retinexformer 같은 프로젝트는 모델 수가 많아 자동 스캔이 가치 있지만, 우리는 Stage가 늘어났을 때 그때 리팩토링하는 것이 합리적입니다. 과한 추상화를 미리 도입하면 신규 기여자가 흐름을 따라가기 어려워집니다.

## Q. FrameExtract에서 블러 필터링을 왜 시간 구간별(chunk)로 나눠서 하나요?

**A.** 단순히 전체 프레임에서 하위 N%를 일괄 컷하면, 모션 블러가 연속된 구간이 통째로 제거됩니다. 그 구간이 카메라가 A지점에서 B지점으로 이동하는 구간이었다면, A와 B 사이의 매칭 포인트가 사라져 COLMAP이 하나의 씬을 두 개로 분리 재구성하게 됩니다. 영상을 chunk로 나눠 각 chunk에서 독립적으로 컷하면, 블러가 심한 구간에서도 "그나마 덜 흐린 프레임"이 최소 보장 장수만큼 살아남아 카메라 궤적의 다리 역할을 합니다.

## Q. 왜 2패스 구조로 프레임을 처리하나요?

**A.** 4K 30fps 30초 영상은 900프레임, 메모리에 전부 올리면 약 22GB입니다. 1패스에서 블러 점수(Laplacian variance)만 계산하고 프레임은 버립니다. 살아남을 인덱스가 확정되면 2패스에서 해당 프레임만 `cap.set()`으로 탐색하여 읽고, 리사이즈 후 즉시 디스크에 저장합니다. 메모리 사용량이 프레임 1장 분량(~24MB)으로 줄어들어 긴 영상이나 고해상도에서도 OOM 없이 동작합니다.

## Q. Stage 인터페이스를 run(config, context)에서 __init__(config) + run(context)로 바꾼 이유는?

**A.** config는 Stage 생명주기 동안 변하지 않는 고정 설정입니다. __init__에서 한 번 꺼내두면 run과 내부 메서드에서 self.X로 깔끔하게 접근 가능하고, "이 Stage가 어떤 config 키를 쓰는지" __init__만 보면 파악됩니다. 또한 config 키 오타 같은 에러가 인스턴스 생성 시점에 터져서 디버깅이 쉬워집니다.

## Q. 3DGS에서 입력 이미지를 정사각형(480x480)이 아닌 종횡비 유지로 리사이즈하는 이유는?

**A.** 3DGS는 카메라 intrinsic(초점거리, 주점)과 이미지 해상도가 정확히 대응해야 합니다. 정사각형으로 찌그러뜨리면 intrinsic이 깨져서 렌더링 결과가 왜곡됩니다. 원본 3DGS 코드도 1/2, 1/4 등 종횡비 유지 다운스케일만 지원하며, 기본값은 긴 변 1600px입니다. 딥러닝 분류는 의미(semantic)만 보므로 정사각형이 가능하지만, 3DGS는 기하학적 정확도가 생명이라 종횡비를 반드시 유지해야 합니다.

## Q. COLMAP을 pycolmap이 아닌 subprocess로 호출한 이유는?

**A.** pycolmap은 Python 바인딩이지만 일부 기능이 미지원되고 CUDA 빌드 이슈가 빈번합니다. COLMAP CLI를 subprocess로 호출하면 바이너리만 교체하여 버전 업데이트가 가능하고, 빌드 의존성이 없어 환경 세팅이 단순합니다. pycolmap은 검증 단계에서 Reconstruction 로드용으로만 사용하고, 실제 SfM 실행은 CLI에 맡기는 것이 가장 안정적입니다.

## Q. Phase 1에서 더미 Stage로 동작 검증을 한 이유는?

**A.** 실제 모델 구현(COLMAP, 3DGS) 전에 **파이프라인 뼈대 자체가 올바르게 동작하는지** 먼저 확인하기 위해서입니다. yaml 파싱, Stage 매핑, Orchestrator 순회, import 경로 등 인프라 단계에서 발생할 수 있는 문제를 모델 구현과 분리해 잡아낼 수 있습니다. 이는 통합 테스트의 기본 원칙(레이어별 분리 검증)과도 일치합니다.
