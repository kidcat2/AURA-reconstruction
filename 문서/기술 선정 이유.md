# 기술 선정 이유

> 프로젝트에서 선택한 기술·모델·방법론에 대해 **왜 이것을 선택했는지**, **장점은 무엇인지**, **대안 대비 어떤 점이 나은지**를 정리한 문서

---

## Stage + Recipe 아키텍처

- **선정 이유** : 3DGS 분야는 새 모델이 빠르게 나오고 있어 고정 파이프라인으로는 대응 불가. Stage를 자유롭게 조합할 수 있는 구조 필요
- **장점** : Stage 파일 하나 추가 + Recipe yaml 작성만으로 새 모델 대응 가능. Orchestrator/기존 Stage 수정 불필요
- **대안** : 고정 5단계 파이프라인 (프레임추출 → SfM → 학습 → 후처리)
- **대안 대비 이점** : End-to-End 모델(SfM 없음), 전처리 추가(동적 물체 제거), 학습 기반 초기화(DUSt3R) 등 단계 수/순서가 다른 모델에 대응 불가
- **근거** : PyTorch Lightning(v2.6.1), Nerfstudio(v1.1.5), FastGS(CVPR 2026) 등 최신 ML/3DGS 프레임워크들이 동일한 패턴 사용

## COLMAP + 원본 3DGS (첫 번째 모델)

- **선정 이유** : 기반 구조를 이해한 상태에서 확장해야 올바른 판단 가능. 원본 3DGS가 COLMAP을 전처리로 사용
- **장점** : 레퍼런스가 가장 풍부. 트러블슈팅, 벤치마크 자료 많음. 파이프라인 검증 기반으로 최적
- **대안** : 최신 모델(Mip-Splatting, 3DGS-MCMC 등)로 바로 시작
- **대안 대비 이점** : 베이스 이해 없이 최신 모델을 쓰면 문제 발생 시 원인 파악 어려움. 원본으로 파이프라인 완성 후 모델 교체하면 아키텍처 설계력도 증명 가능

## Python 3.10 + PyTorch 2.1.2 + CUDA 11.8

- **선정 이유** : 원본 3DGS 커스텀 CUDA 커널(diff-gaussian-rasterization)이 CUDA 11.8에서 가장 많이 테스트됨
- **장점** : PyTorch + COLMAP + OpenCV 호환성이 가장 안정적인 조합
- **대안** : CUDA 12.x + PyTorch 최신
- **대안 대비 이점** : CUDA 12.x에서 커스텀 커널 컴파일 이슈 보고 있음. 안정성 우선

## conda + pip 분리 설치

- **선정 이유** : conda로 PyTorch를 설치하면 Windows에서 MKL/OpenMP DLL 충돌 발생
- **장점** : conda는 Python 환경 관리만, PyTorch 및 패키지는 pip + --index-url로 CUDA 버전 일치시켜 설치. DLL 충돌 원천 차단
- **대안** : conda로 전부 설치
- **대안 대비 이점** : conda PyTorch 패키지의 libiomp5md.dll과 libomp.dll 충돌 방지

## PyYAML

- **선정 이유** : Recipe(파이프라인 조합)를 yaml 파일로 정의하고, Registry에서 Stage 클래스를 찾아 실행하기 위한 yaml 파서
- **장점** : 경량. 코드 수정 없이 yaml만 바꿔서 다른 파이프라인 실행 가능
- **대안** : JSON, TOML, Python dict 하드코딩
- **대안 대비 이점** : yaml이 가독성 가장 좋음. ML 업계 표준 (Hydra, MMEngine, ZenML 등 모두 yaml 사용)

## 단일 recipes.yaml + recipe 키 선택 방식

- **선정 이유** : Recipe마다 yaml 파일을 따로 두면 새 모델 추가 시 파일이 계속 늘어남. 하나의 yaml에 여러 recipe를 키로 묶어두고 `--recipe` 인자로 키만 선택하는 방식이 더 단순
- **장점** : 새 조합 추가 시 yaml에 블록 하나만 추가, 파일 생성 불필요. 모든 조합을 한 곳에서 비교 가능
- **대안** : recipe별로 yaml 파일 분리 (`colmap_3dgs.yaml`, `dust3r_3dgs.yaml`, …)
- **대안 대비 이점** : 파일 수가 늘지 않음. recipe 간 차이를 yaml 한 파일에서 바로 확인 가능

## 단순 STAGE 딕셔너리 (자동 스캔/register 메서드 미채택)

- **선정 이유** : Phase 1 단계의 Stage가 4개뿐이라 동적 등록 메커니즘은 과한 추상화. 단순 딕셔너리가 가독성과 명시성 모두 우수
- **장점** : "어떤 이름이 어떤 클래스로 매핑되는지" 한 파일만 보면 즉시 파악 가능. 디버깅/추적 용이
- **대안** : (1) `register()` 메서드 패턴, (2) 폴더 자동 스캔 + `importlib`
- **대안 대비 이점** : 자동 스캔은 Stage 수가 수십 개로 늘어났을 때만 가치 있음. 지금 도입하면 마법(magic) 코드가 되어 신규 기여자가 흐름을 따라가기 어려움. Stage가 늘어나면 그때 리팩토링 (Retinexformer 등이 사용하는 패턴 참고)

## Laplacian Variance 블러 검출

- **선정 이유** : 프레임 추출 시 블러 프레임을 걸러내야 함. COLMAP 매칭 품질에 직결
- **장점** : OpenCV 한 줄(`cv2.Laplacian().var()`)로 구현 가능. 2차 미분 분산이라 엣지 강도를 직접 수치화. ms 단위로 빠름
- **대안** : FFT 기반 주파수 분석, 학습 기반 블러 검출 (DeblurGAN 등)
- **대안 대비 이점** : FFT는 구현 복잡도 대비 정확도 차이 미미. 학습 기반은 추가 모델 로딩 필요하고 프로토타입 단계에 과함

## 시간 구간별(chunk) 블러 컷

- **선정 이유** : 단순 하위 N% 컷은 연속 블러 구간을 통째로 제거하여 카메라 궤적이 끊길 수 있음
- **장점** : 영상을 chunk로 나눠 각 chunk에서 독립 컷. chunk당 최소 보장 장수로 궤적 끊김 방지
- **대안** : 전체 점수 기준 하위 N% 일괄 컷
- **대안 대비 이점** : 일괄 컷은 중간에 블러 텀이 길면 COLMAP이 두 그룹으로 분리 재구성됨. chunk별 컷은 시간 분포를 보존

## 2패스 프레임 처리 (메모리 최적화)

- **선정 이유** : 전체 프레임을 메모리에 올리면 4K 30초 영상 기준 ~22GB. OOM 발생
- **장점** : 1패스에서 블러 점수만 계산(프레임 미저장), 2패스에서 살아남은 idx만 읽어서 리사이즈+저장. 메모리 사용량 프레임 1장 분량
- **대안** : 전체 프레임을 리스트에 저장 후 필터링
- **대안 대비 이점** : 메모리 22GB → ~24MB. 긴 영상/고해상도에서도 안정 동작

## 외부 COLMAP 바이너리 호출 (subprocess)

- **선정 이유** : COLMAP은 C++로 작성된 SfM 도구로, Python 바인딩(pycolmap)보다 CLI가 안정적이고 기능이 완전함
- **장점** : subprocess로 호출하면 COLMAP 버전 업데이트 시 바이너리만 교체하면 됨. 빌드 의존성 없음
- **대안** : pycolmap으로 Python 네이티브 호출
- **대안 대비 이점** : pycolmap은 일부 기능 미지원, CUDA 빌드 이슈 빈번. CLI 호출이 가장 범용적이고 트러블슈팅 자료 풍부

## pycolmap.Reconstruction으로 .bin 파일 로드

- **선정 이유** : COLMAP이 생성한 cameras/images/points3D.bin을 Python에서 읽어야 함. 실행은 CLI, 로드는 pycolmap으로 역할 분리
- **장점** : 한 줄(`pycolmap.Reconstruction(path)`)로 세 파일 한 번에 파싱. 카메라/이미지/포인트가 dict 객체로 제공되어 접근 간편
- **대안** : .bin 포맷 직접 파싱 (struct 모듈)
- **대안 대비 이점** : .bin은 가변 길이 레코드와 엔디안 처리가 필요한 복잡한 포맷. 직접 파싱은 유지보수 부담. CLI와 Python 바인딩을 역할별로 병용하는 것이 가장 실용적

## KDTree 기반 가우시안 scale 초기화

- **선정 이유** : 초기 가우시안의 scale은 주변 포인트와의 간격을 반영해야 자연스럽게 씬을 덮음
- **장점** : 각 포인트의 k-최근접 이웃 평균 거리로 scale 설정 → 밀집 영역은 작은 가우시안, 희박 영역은 큰 가우시안. 원본 3DGS 구현과 동일 전략
- **대안** : 모든 가우시안에 동일한 상수 scale 부여
- **대안 대비 이점** : 상수 scale은 밀집 영역에서 과도한 오버랩, 희박 영역에서 구멍 발생. 학습 초반부터 손실이 커져 수렴 지연

## SH DC 계수 변환으로 색상 초기화

- **선정 이유** : 3DGS는 색상을 Spherical Harmonics 계수로 표현. 초기 RGB를 0번째 SH 계수(DC term)로 변환 필요
- **장점** : SH 기저 함수 Y₀ = 1/(2√π) ≈ 0.28209의 역변환 공식 `(rgb/255 − 0.5) / 0.28209`로 정확한 초기값 계산. 학습 초기부터 COLMAP 색상을 그대로 재현
- **대안** : RGB를 그대로 f_dc에 대입 / 0으로 초기화하고 학습에만 맡기기
- **대안 대비 이점** : 변환 없이 RGB 원본을 넣으면 렌더링이 약 0.28배로 어둡게 나옴. 0 초기화는 초기 손실이 커져 수렴 지연. 수학적으로 올바른 변환이 학습 안정성 확보

## 절대 경로 import (`from aura.xxx import ...`)

- **선정 이유** : 상대 경로(`from ..base import BaseStage`)는 폴더 구조가 깊어질수록 어느 모듈을 가리키는지 한눈에 안 보임. PEP 8도 절대 경로 권장
- **장점** : 어디서 import하는지 명확. IDE 자동완성/리팩토링 도구와의 호환성 우수
- **대안** : 상대 경로 import
- **대안 대비 이점** : 패키지명(`aura`)이 모든 import문에 명시되어 있어 가독성·일관성 확보. 폴더 이동 시에도 안정적
