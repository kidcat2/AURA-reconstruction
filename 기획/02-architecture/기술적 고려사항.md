# 기술적 고려사항

---

## 파이프라인

### 1. 영상 수신 및 입력 준비

- [대용량 영상] 4K·장시간 영상은 수 GB → S3 단일 PUT 5GB 제한. 초과 시 멀티파트 업로드 필요
- [업로드 중단·재개] 네트워크 불안정 시 대용량 업로드가 끊기면 처음부터 → 멀티파트 업로드로 이어올리기 지원 필요
- [Lambda 콜드 스타트] 첫 실행 시 0.5~3초 지연. 비동기 처리이므로 사용자 경험에 영향 적음
- [GPU 시작 실패] AWS 용량 부족 시 인스턴스 시작 불가 → 실패 시 DB에 에러 기록 + 재시도 로직 필요

### 2. 전처리 및 초기 구조 추출

- [실패 조기 감지] 실패 시 GPU 즉시 종료하여 비용 낭비 방지
- [촬영 가이드] 실패 원인 대부분이 잘못된 촬영. 업로드 전 사용자 안내가 실패율을 낮추는 가장 효율적인 방법
- [SfM 구현체 교체] 더 나은 방식으로 교체할 수 있도록 인터페이스 설계 필요
- [타임아웃] 복잡한 장면에서 SfM이 수십 분~수 시간 걸릴 수 있음 → 타임아웃 후 실패 처리

### 3. Gaussian 생성

- [학습 중단 시 복구] GPU 비정상 종료 시 작업 유실 → 체크포인트 저장으로 재개 기능 필요
- [GPU 메모리 초과] 복잡한 장면에서 메모리 부족 → 자동 품질 저하 재시도 처리 필요
- [3DGS 구현체 교체] Docker 컨테이너 내에서 모델 실행부만 교체 가능하도록 인터페이스 설계 필요

### 4. 결과물 전달

- [파이프라인 오류 전달] 단계별 실패 원인과 재시도 안내 메시지 설계 필요
- [모니터링] 운영자가 잡 상태를 파악할 수 있는 관리 도구 필요
- [대용량 .splat] 수백 MB 파일의 모바일 다운로드 → 압축 전송 또는 스트리밍 검토

## 웹

### .splat 뷰어 + 씬 편집

- [대용량 .splat 로딩] 수백 MB .splat 파일의 브라우저 로딩 시간 → 프로그레시브 로딩 또는 LOD(Level of Detail) 전략 필요
- [VRM 호환성] VRM 버전별 차이, 쉐이더 호환 등 → 지원 범위 명확히 정의 필요
- [WebGL 메모리 한계] 브라우저 GPU 메모리 제한으로 복잡한 씬에서 크래시 가능 → 최대 파일 크기 제한 또는 경고 필요
