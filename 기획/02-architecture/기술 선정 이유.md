# 기술 선정 이유

---

## 저장소 - S3 (AWS)

- 사용 : 사용자가 올린 영상과 파이프라인 결과물(.splat)을 저장할 공간
- 왜 필요한가 : 웹 서버에 파일을 저장하면 500명이 동시에 올릴 때 서버 디스크·대역폭이 터짐. 파일 저장을 서버와 분리해야 함
- 왜 S3인가 : 용량 무제한, 브라우저에서 직접 업로드/다운로드 가능, Lambda·CloudFront 등 AWS 생태계와 자연스럽게 연동
- 대안 1 : Google Cloud Storage (GCS) → 기능은 동등하지만 GPU·Lambda·CDN을 모두 AWS로 통일하는 편이 운영 복잡도가 낮음
- 대안 2 : Azure Blob Storage → 동일한 이유. AWS 생태계를 선택한 이상 저장소도 통일
- 대안 3 : MinIO (자체 호스팅 S3 호환) → 직접 서버를 관리해야 함. 소규모 팀에서 인프라 운영 부담

## 업로드 보안 - Presigned URL

- 사용 : 브라우저가 S3에 직접 파일을 올리거나 내려받을 때 임시 접근 권한을 발급
- 왜 필요한가 : S3를 아무나 접근할 수 있게 열어두면 외부인이 파일을 올리거나 남의 파일을 볼 수 있음
- 왜 Presigned URL인가 : "이 파일 하나만, 이 시간 안에만" 허용하는 임시 URL이라 S3 접근 키를 브라우저에 노출하지 않으면서도 직접 통신 가능
- 대안 1 : AWS IAM 임시 자격 증명 (STS) → Presigned URL보다 설정이 복잡하고, 단순 파일 업로드/다운로드에는 과한 구조
- 대안 2 : S3 퍼블릭 액세스 → 보안 없음. 누구든 업로드/열람 가능

## GPU 트리거 - Lambda (AWS)

- 사용 : S3에 영상이 올라오면 자동으로 GPU를 켜는 역할
- 왜 필요한가 : GPU 서버는 꺼져 있으므로 "누군가"가 켜줘야 함. 그 "누군가"를 위해 상시 서버를 돌리는 건 낭비
- 왜 Lambda인가 : 하는 일이 "GPU 켜줘" 한 줄이라 이벤트 발생 시에만 실행되는 서버리스 함수가 적합. 비용은 호출당 과금
- 대안 1 : AWS Step Functions → 복잡한 워크플로우 오케스트레이션 도구. "GPU 켜줘" 한 줄에는 과한 구조
- 대안 2 : Amazon EventBridge → 이벤트 라우팅에 특화. S3 → Lambda가 이미 네이티브로 지원되므로 별도 도입 불필요
- 대안 3 : 상시 서버(FastAPI)가 큐를 감시 → 아무도 안 써도 서버 비용 발생

## GPU - 클라우드 GPU (AWS EC2 + Auto Scaling)

- 사용 : 전처리(SfM) + 3DGS 학습을 실행하는 서버. 작업당 1대 할당, 완료 후 종료
- 왜 필요한가 : 로컬 PC GPU 1대로는 한 명씩만 처리 가능. 500명이면 500대가 동시에 필요
- 왜 AWS EC2 + Auto Scaling인가 : 요청 수만큼 자동으로 GPU가 늘어나고 완료 즉시 종료. 안 쓰는 시간에는 비용 0. AWS 생태계(S3, Lambda, DB)와 동일 리전 배치 가능
- 대안 1 : RunPod → GPU 비용이 AWS 대비 1/4~1/5로 저렴하나 오토스케일링이 약하고 안정성이 부족. 소규모(~200명)에서는 유효
- 대안 2 : Vast.ai → RunPod과 유사. 개인 GPU를 렌탈하는 구조라 가용성이 불안정
- 대안 3 : Google Cloud GPU (GCE) → 기능은 동등하지만 나머지 인프라를 AWS로 통일한 이상 리전·네트워크 비용 면에서 불리
- 대안 4 : 자체 GPU 서버 → 초기 구매 비용이 크고 유지보수 필요. 월 클라우드 비용이 GPU 구매 비용을 넘어서는 시점(2000명+)에서 검토

## GPU 인스턴스 사양 - g5.2xlarge (AWS)

- 사용 : 전처리 단계에서 SfM이 CPU를, 3DGS 학습이 GPU를 집중적으로 사용
- 왜 필요한가 : GPU만 좋고 CPU가 약하면 SfM 단계에서 병목이 걸려 전체 파이프라인이 느려짐
- 왜 g5.2xlarge인가 : NVIDIA A10G GPU(24GB) + 8 vCPU로 GPU와 CPU 성능이 모두 충분한 균형 타입. 시간당 ~$1.2
- 대안 1 : g4dn.xlarge → GPU(T4, 16GB)가 약해서 복잡한 장면에서 메모리 부족 가능
- 대안 2 : p3.2xlarge → V100 GPU로 성능은 좋지만 비용이 g5 대비 2배 이상
- 대안 3 : g6.2xlarge → 최신 세대지만 리전별 가용성이 아직 제한적

## DB - PostgreSQL (AWS RDS)

- 사용 : 파이프라인 잡 상태(진행 중/완료/실패), 사용자 정보, 공간 라이브러리 목록을 기록
- 왜 필요한가 : 잡 상태를 메모리에만 두면 서버 재시작 시 전부 날아감. 브라우저가 "내 작업 어디까지 됐어?"를 물을 때 즉시 응답할 수 있는 영구 저장소 필요
- 왜 PostgreSQL인가 : GPU 기반 AI 서비스 업계 표준 (Replicate, Runway 등). JSON 타입 네이티브 지원. managed DB(RDS)로 서버 관리 불필요. SQLite에서 전환 시 쿼리 문법이 거의 동일
- 대안 1 : MySQL (RDS) → 기능적으로 비슷하지만 JSON 타입 지원·확장성 면에서 PostgreSQL이 우세. AI 업계에서 사실상 표준이 PostgreSQL
- 대안 2 : Amazon DynamoDB → AWS 종속 NoSQL. 관계형 쿼리(JOIN) 불가. 단순 key-value에는 적합하지만 다양한 조건 조회에 부적합
- 대안 3 : Supabase (managed PostgreSQL) → PostgreSQL 기반이라 기능 동일. RDS 대비 설정이 간편하나 대규모에서 커스터마이징 제한
- 대안 4 : Amazon ElastiCache (Redis) → 메모리 기반이라 빠르지만 재시작 시 데이터 유실. 캐시로는 적합하나 영속 저장에는 부적합

## 결과물 서빙 - CloudFront (AWS CDN)

- 사용 : 완성된 .splat 파일을 브라우저에 빠르게 전달
- 왜 필요한가 : .splat은 수십~수백 MB라 S3에서 직접 내려받으면 거리에 따라 느릴 수 있음
- 왜 CloudFront인가 : S3와 같은 AWS 생태계로 설정이 간편. 전 세계 엣지 서버에 캐싱하여 가장 가까운 곳에서 전달
- 대안 1 : Cloudflare CDN → 무료 티어가 강력하지만 S3 연동 시 추가 설정 필요. AWS 내부 통신 비용 절감 이점 없음
- 대안 2 : Fastly → 실시간 캐시 퍼지에 강점이 있으나 .splat 서빙 용도에서는 CloudFront와 차이 없음. 비용이 더 높음
- 대안 3 : CDN 없이 S3 직접 다운로드 → 가능하지만 대용량 파일에서 속도 차이 체감

## 상태 알림 - 폴링

- 사용 : 브라우저가 파이프라인 진행 상황을 5초마다 DB에 확인
- 왜 필요한가 : GPU는 별도 서버에서 돌아가므로 브라우저가 직접 진행 상황을 알 수 없음
- 왜 폴링인가 : 구현이 단순. 500명 × 5초 = 초당 100쿼리는 PostgreSQL이 충분히 감당
- 대안 1 : WebSocket → 서버가 브라우저에 직접 푸시. 실시간이지만 연결 관리 필요. 수천 명 이상에서 전환 검토
- 대안 2 : SSE (Server-Sent Events) → WebSocket보다 단순하지만 단방향. 역시 연결 관리 필요
- 대안 3 : AWS AppSync (GraphQL Subscriptions) → 실시간 푸시 지원하나 도입 복잡도가 높고 이 용도에는 과한 구조

## 인증 - JWT

- 사용 : 사용자를 식별하고, 본인 결과물만 접근할 수 있도록 제한
- 왜 필요한가 : 인증이 없으면 URL만 알면 누구든 남의 결과물에 접근 가능
- 왜 JWT인가 : 상태 비저장(stateless)이라 서버가 여러 대여도 별도 공유 없이 동작
- 대안 1 : 세션 기반 인증 (express-session 등) → 서버에 세션을 저장해야 하므로 서버가 여러 대일 때 Redis 등 세션 공유 인프라 추가 필요
- 대안 2 : AWS Cognito → 인증 전체를 AWS에 위임. 편리하지만 AWS 종속이 깊어지고 커스터마이징 제한
- 대안 3 : Auth0 / Firebase Auth → 외부 서비스 의존. 무료 티어 제한 있고 비용 발생

## 프론트엔드 - React + TypeScript

- 사용 : 브라우저에서 동작하는 UI 전체. .splat 뷰어, 3D 모델 배치, 씬 조작, 스크린샷 등
- 왜 필요한가 : 3D 씬 조작은 실시간 인터랙션이 핵심. 페이지 새로고침 없이 상태를 유지하며 조작할 수 있는 SPA(Single Page Application) 프레임워크가 필요
- 왜 React인가 : 컴포넌트 기반 구조로 3D 뷰어·UI 패널·파일 업로더 등을 독립적으로 개발 가능. three.js(@react-three/fiber) 등 3D 관련 생태계가 가장 풍부. TypeScript와의 조합으로 타입 안정성 확보
- 대안 1 : Vue.js → 3D 관련 생태계(three.js 래퍼 등)가 React 대비 빈약. 커뮤니티·레퍼런스 규모 차이
- 대안 2 : Svelte → 번들 크기가 작고 성능이 좋지만 three.js 통합 생태계가 아직 미성숙
- 대안 3 : Vanilla JS (프레임워크 없음) → 초기에는 단순하지만 UI가 복잡해지면 상태 관리가 어려워짐. 컴포넌트 재사용 불가

## 백엔드 - FastAPI (Python)

- 사용 : API 서버 전체. 파이프라인 API + 인증 + Presigned URL 발급 + 공간 라이브러리 API + 프론트엔드 정적 파일 서빙
- 왜 필요한가 : 파이프라인이 Python이므로 백엔드도 Python으로 통일하면 언어·서버가 하나로 줄어듦
- 왜 FastAPI인가 : 파이프라인 코드와 같은 Python. 비동기 지원으로 동시 요청 처리에 적합. 자동 API 문서(Swagger) 생성. 프론트엔드는 React 빌드 결과물(HTML/JS/CSS)을 정적 파일로 서빙
- 대안 1 : Node.js (Express / Next.js) → 별도 언어·런타임 도입. 웹 서버가 하는 일(인증, URL 발급, DB 조회)이 Python으로 충분한 수준이라 Node.js를 추가할 이유가 약함
- 대안 2 : Django (Python) → 풀스택 프레임워크라 기능이 많지만 이 프로젝트에서는 과한 구조. FastAPI가 더 가볍고 비동기 성능이 우수
- 대안 3 : Flask (Python) → 간단하지만 비동기 지원이 기본이 아님. FastAPI가 현대적 대안

## 렌더링 엔진 - WebGL

- 사용 : 브라우저에서 .splat과 3D 모델(VRM·GLB)을 실시간 렌더링
- 왜 필요한가 : 브라우저에서 3D를 그리려면 GPU를 직접 제어할 수 있는 API가 필요
- 왜 WebGL인가 : 모든 최신 브라우저가 지원하는 유일한 3D 렌더링 표준. 성숙한 생태계 (three.js 등)
- 대안 1 : WebGPU → 차세대 표준. 성능 우수하지만 Safari·Firefox 지원이 아직 제한적. 확장2에서 전환 검토
- 대안 2 : CSS 3D Transforms → 단순 3D 효과에만 적합. 실시간 Gaussian Splatting 렌더링 불가

## 컨테이너 - Docker

- 사용 : 파이프라인 실행 환경을 컨테이너로 패키징. 로컬 PC든 클라우드든 동일하게 실행
- 왜 필요한가 : 로컬 PC → 클라우드 GPU로 이전할 때 환경을 다시 셋업하면 구조를 뜯어야 함
- 왜 Docker인가 : 컨테이너 업계 표준. 어디서든 docker run 하나로 동작. 확장 시 클라우드 GPU에 올릴 때 환경 재현성 보장
- 대안 1 : Podman → Docker 호환이지만 GPU 패스스루 설정이 Docker 대비 복잡. 생태계가 작음
- 대안 2 : Singularity/Apptainer → HPC/연구용 컨테이너. 클라우드 GPU 환경에서는 Docker가 표준
- 대안 3 : 컨테이너 없이 직접 설치 → 환경마다 설치 과정이 다르고 재현성 없음
